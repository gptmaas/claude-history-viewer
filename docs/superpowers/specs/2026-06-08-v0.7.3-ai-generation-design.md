# CodeMemory v0.7.3 — AI Generation & Technical Review Design Spec

## Overview

v0.7.2 delivered complete pipeline data model, state machine, CRUD UI, and 10 API endpoints with zero AI/LLM integration. v0.7.3 introduces AI-powered generation and review across the first three pipeline stages: requirement completion, product design & review, and technical design & review.

Core constraint: AI generates content, humans confirm. No automatic code modification, no automated releases.

## Decisions

- **LLM Provider**: Anthropic Claude via `@anthropic-ai/sdk`
- **Architecture**: Direct SDK calls in existing API route pattern (no extra abstraction layer)
- **Scope**: All three phases delivered together (7.3A + 7.3B + 7.3C)
- **API Key Management**: Manual configuration via Settings page, stored in local SQLite

## 1. AI Configuration Storage

### Schema

New `ai_config` table in local SQLite:

```sql
CREATE TABLE ai_config (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  name TEXT NOT NULL,
  description TEXT,
  provider TEXT NOT NULL DEFAULT 'anthropic',
  api_key TEXT,
  base_url TEXT,
  model TEXT NOT NULL DEFAULT 'claude-sonnet-4-6-20250627',
  is_active INTEGER NOT NULL DEFAULT 1,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
)
```

Fields:
- `name` — User-facing label ("默认配置", "公司代理")
- `description` — Optional notes
- `provider` — Provider identifier, currently only `'anthropic'`
- `api_key` — Anthropic API Key
- `base_url` — Optional custom endpoint (proxy, self-hosted compatible API)
- `model` — Model identifier, defaults to `claude-sonnet-4-6-20250627`
- `is_active` — Only one config active at a time; activating one deactivates others

### Settings API

`/api/settings/ai` route:
- `GET` — List all configs, mask API keys in response (`sk-...xxxx`)
- `POST` — Create new config (body: name, description, provider, apiKey, baseUrl, model)
- `PATCH` — Update config (body: id + fields to update)
- `DELETE` — Delete config by id

### Settings Page UI

New "AI 配置" section on Settings page:
- Config list displayed as cards (name, provider, model, active badge)
- Add/Edit dialog with fields: name, description, provider dropdown (locked to Anthropic), API Key input, Base URL input (optional, shows default hint), Model dropdown with presets + custom input
- "设为活跃" toggle, delete action
- API Key shows masked value, editable only in edit mode

## 3. Repo Scanner

### `lib/ai/repo-scanner.ts`

Scans a project directory to extract code context for the technical design phase.

Input: project root path (configured in Settings, defaults to current working directory)

Output: structured context object containing:
- File tree summary (top 3 levels, excluding node_modules, .git, dist, build, .next)
- `package.json` summary (name, dependencies, scripts)
- Route/API directory listing (if `app/api/` or `pages/api/` exists)
- Data model file listing (if `lib/db/` or `prisma/` exists)
- Component directory listing (if `components/` exists)
- Recent git diff stat (last 10 commits, if git repo)
- Key config files content (tsconfig, next.config, etc.)

Output is a string summary capped at ~4000 tokens. Scanner truncates individual file contents to 500 lines max and total output to stay within this budget. If the project is too large, scanner prioritizes: package.json > schema files > route files > component files > config files > git diff.

Settings page will have a "项目目录" field for configuring the scan target.

## 4. Unified Generation API

### `POST /api/pipeline/generate`

Single endpoint for all generation operations.

Request:
```typescript
{
  itemId: number
  stageKey: 'idea' | 'product_design_review' | 'technical_design_review'
  generateType: 'requirement' | 'product_design' | 'product_review'
              | 'technical_design' | 'tech_review' | 'task_breakdown' | 'test_plan'
  context?: {
    sessionExcerpt?: string      // For requirement generation from session
    manualNotes?: string          // User-provided additional context
  }
}
```

Response:
```typescript
{
  content: string              // Generated markdown or JSON string
  artifactName: string         // Suggested artifact name
  artifactType: string         // 'markdown' or 'json'
  isReview?: boolean           // If true, content should also be saved as auto review
  reviewResult?: 'approved' | 'needs_changes'  // For review generateTypes
  risks?: PipelineRisk[]       // Risk items (for tech_review, product_review)
  gateResult?: PipelineGateResult  // Gate check result (for requirement)
}
```

Flow:
1. Read item + all existing artifacts from prior stages
2. For `technical_design_review` stages: run repo scanner
3. Build prompt using the appropriate template
4. Call `generateText()` via Anthropic SDK
5. Parse response, extract risks if review type
6. Return to frontend for preview

## 5. Generation Flows Per Phase

### Phase 7.3A: Requirement Generation

Trigger: "AI 补全需求" button on `idea` stage card.

Inputs:
- item.title, item.background (user may have only typed a one-liner)
- sourceSessionId session content (if linked)
- user-provided manual notes (optional)

Generated artifacts:
- **需求说明** (markdown) — background, user goals, use cases, scope boundaries, non-goals
- **验收标准** (JSON array) — verifiable acceptance criteria
- **澄清问题** (markdown) — ambiguous points needing user response

Gate check after generation:
- Requirement goals not empty
- At least one acceptance criteria
- Scope boundaries not empty
- Zero P0 blockers

Gate passes → stage transitions to `waiting_review`. User confirms to advance.

### Phase 7.3B: Product Design & Review

Trigger: "生成产品方案" and "生成产品评审" buttons on `product_design_review` stage card.

Inputs:
- All `idea` stage artifacts (requirement, acceptance criteria)
- item.goals, item.acceptanceCriteria

Generated artifacts:
- **产品方案** (markdown) — user flows, page/module changes, information architecture, edge cases, interaction rules, acceptance use cases, product risks
- **产品评审报告** (saved as auto review, reviewerType='auto') — checklist review across 6 dimensions:

Review dimensions:
1. Does it solve the original requirement?
2. Is there a clear user path?
3. Does it cover empty state, error state, loading state?
4. Is it verifiable?
5. Does it fit the current product form?
6. Is there unnecessary complexity?

Each dimension: pass/fail/attention-needed + explanation.

Review saved → stage enters `waiting_review`. User must explicitly approve.

### Phase 7.3C: Technical Design & Task Breakdown

Trigger: Four buttons on `technical_design_review` stage card:
- "生成技术方案"
- "生成任务拆分"
- "生成技术评审"
- "生成测试计划"

Inputs:
- All prior stage artifacts
- Repo scanner output (project code context)

Generated artifacts:
- **技术方案** (markdown) — affected files/modules, data model changes, API design, frontend component design, test strategy, migration strategy, rollback strategy, risk list
- **任务拆分** (JSON array) — each task: title, description, estimatedComplexity, dependencies, riskLevel (P0-P3)
- **测试计划** (markdown) — test scope, test commands, expected outcomes
- **技术评审报告** (saved as auto review) — per-item review with P0-P3 risk classification

Risk output integrates with existing `PipelineRisk[]` and `PipelineGateResult`.

## 6. UI Components

### Generate Dialog (`components/pipeline/generate-dialog.tsx`)

Shared dialog for all generation operations:
- Props: `itemId`, `stageKey`, `generateType`
- States: idle → generating (spinner + "正在生成...") → preview → saving
- Preview: rendered markdown with edit capability (textarea)
- Actions: "重新生成" / "保存为产物"
- On save: calls existing `addArtifact` API, optionally `addReview` for review types
- After save: refreshes stage card data

### AI Config Section (`components/pipeline/ai-config-section.tsx`)

Settings page component:
- Card list of AI configs
- Add/Edit dialog
- Active toggle, delete action
- API Key masked display

### Stage Card Modifications (`components/pipeline/stage-card.tsx`)

For stages `idea`, `product_design_review`, `technical_design_review`:
- Show generation buttons based on stageKey (see mapping table in Section 5)
- Buttons disabled if no active AI config
- Each button opens GenerateDialog with the corresponding generateType

## 8. Non-Goals

- No code modification or execution
- No test running
- No automatic git commit/push
- No build or release actions
- No streaming/SSE generation (may add later)
- No multi-provider support beyond Anthropic (schema supports future extension)

## 9. Acceptance Criteria

- [ ] User can configure Anthropic API Key in Settings, stored in local SQLite
- [ ] User can generate requirement completion from the idea stage
- [ ] User can generate product design and product review from the product_design_review stage
- [ ] User can generate technical design, task breakdown, test plan, and tech review from the technical_design_review stage
- [ ] Repo scanner extracts project context and feeds it to technical design prompts
- [ ] All generated content is previewable and editable before saving
- [ ] Saved content integrates with existing artifact and review system
- [ ] Auto reviews use reviewerType='auto'
- [ ] No AI generation executes without active API configuration
- [ ] API Key never exposed in client-side rendering (masked in API responses)
