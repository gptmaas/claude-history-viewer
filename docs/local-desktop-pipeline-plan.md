# CodeMemory v0.7 主规划 — 个人本地桌面版与自动化产品开发流水线

## 1. 产品定位

当前 CodeMemory 已经可以作为本地 Web Viewer 查看 Claude Code 历史。下一阶段个人本地版本应升级为一个真正的桌面 App：

- 打开即用，不要求用户手动启动 `npm run dev` 或配置服务。
- 打开首页就是 Dashboard，直接看到最近 AI Coding 活动。
- 能稳定查看本地会话记录、搜索、项目、分析和导出。
- 在本地构建一个“全自动产品开发流水线”，把需求想法、方案、评审、编码、测试、验收、发布串成可追踪、可自动流转的工作台。

核心目标不是再做一个聊天窗口，而是把 AI Coding 的过程变成结构化工程流水线：每个阶段都有输入、产物、质量门禁、评审结果和自动流转条件。

## 2. 桌面 App 目标形态

### 2.1 启动体验

目标：

- 用户双击 App 后进入 Dashboard。
- 首次启动自动扫描本机 AI Coding 数据源。
- 默认支持 Claude Code 和 Codex CLI。
- 无需登录、无需云端、无需 API Key。
- 数据全部保存在本机。

首次启动流程：

1. 检测 `~/.claude`、`~/.codex` 等默认目录。
2. 如果找到数据源，自动开始索引。
3. 如果未找到数据源，进入设置页，让用户选择目录。
4. 索引完成后进入 Dashboard。
5. 后续启动直接读取本地索引并后台增量刷新。

### 2.2 桌面技术路线

当前项目已有 Tauri CLI 依赖和脚本，但还没有完整 `src-tauri` 目录。

推荐路线：

- 使用 Tauri v2 作为桌面壳。
- 前端继续复用现有 Next.js 页面与组件。
- 本地数据层从“实时读 JSONL 文件”演进为“本地数据库索引”。
- 桌面端通过 Tauri capability 安全访问用户授权的数据目录。

需要决策的关键点：

- 短期可用方案：Tauri 启动内置本地 Next server，桌面窗口访问本地地址。
- 中期推荐方案：拆出纯客户端 UI + 本地 API/SQLite 服务，减少 Next server 打包复杂度。
- 长期理想方案：Tauri Rust 后端负责文件扫描、索引、SQLite 查询，前端只负责展示。

阶段建议：

- MVP 先使用“内置本地服务 + Tauri 窗口”降低迁移成本。
- 等桌面版稳定后，再把本地数据处理下沉到 Tauri 后端或独立 local engine。

### 2.3 本地数据存储

当前本地模式直接读 `~/.claude` 文件，适合轻量查看，但不适合复杂流水线。

桌面版建议引入本地 SQLite：

- 保存已解析会话、消息、项目、数据源、索引状态。
- 保存流水线项目、需求、方案、评审、任务、测试、验收、发布记录。
- 支持快速搜索和离线分析。
- 支持后续与云端同步，但不强依赖云端。

建议表模型：

- `local_sources`：本地数据源配置。
- `local_raw_files`：原始文件索引和 hash。
- `local_sessions`：会话。
- `local_messages`：消息。
- `pipeline_projects`：流水线项目。
- `pipeline_items`：需求/想法条目。
- `pipeline_stages`：阶段状态。
- `pipeline_artifacts`：阶段产物。
- `pipeline_reviews`：评审记录。
- `pipeline_tasks`：开发任务。
- `pipeline_test_runs`：测试运行。
- `pipeline_releases`：发布记录。
- `pipeline_events`：状态流转事件日志。

### 2.4 本地后台能力

桌面版需要一个本地后台进程或 Tauri 后端能力：

- 文件扫描。
- 文件监听。
- 增量解析。
- 本地索引。
- 搜索。
- 流水线任务调度。
- 调用 AI Coding CLI。
- 执行测试命令。
- 收集测试结果。
- 生成评审报告。

这部分不建议全部塞进 React 页面，应抽象成 local engine。

## 3. 桌面版基础功能规划

### 3.1 Dashboard

打开 App 默认展示 Dashboard。

基础指标：

- 今日会话数。
- 今日消息数。
- 最近 7 天消息趋势。
- 活跃项目。
- 最近进行中的流水线项目。
- 等待用户确认的门禁。
- 最近失败的自动化任务。

桌面版 Dashboard 不应只是数据看板，还应成为工作入口：

- 继续最近项目。
- 新建需求想法。
- 查看待评审项。
- 查看测试失败项。
- 查看待发布项。

### 3.2 会话记录

继续保留并强化：

- 会话列表。
- 会话详情。
- 项目筛选。
- 来源筛选。
- 机器/本机信息。
- 搜索。
- 导出。
- 收藏/标记关键会话。
- 从会话生成需求、任务、技术方案或复盘。

新增能力：

- 会话与流水线阶段关联。
- 从某段对话提取决策。
- 从工具调用提取改动文件、测试命令和错误信息。
- 将会话作为某个阶段的证据材料。

### 3.3 设置

本地桌面版设置应包括：

- 数据源目录管理。
- 支持来源开关：Claude Code、Codex CLI，后续 Cursor/Windsurf。
- 本地数据库位置。
- 索引状态和重建索引。
- AI CLI 配置：Codex、Claude Code 或其他执行器。
- 默认项目目录。
- 默认测试命令。
- 自动流转策略。
- 发布命令白名单。

## 4. 自动化产品开发流水线

### 4.1 流水线阶段

目标流水线：

1. 需求想法
2. 方案设计与评审
3. 技术方案与评审
4. 开发编码与单元自测
5. 集成测试
6. 需求验收
7. 发布

每个阶段都需要：

- 输入。
- 自动生成或人工补充的产物。
- 质量门禁。
- 评审结论。
- 流转条件。
- 事件日志。
- 可追溯证据。

### 4.2 阶段一：需求想法

输入来源：

- 用户手动输入一句想法。
- 从历史会话中提取需求。
- 从错误日志、TODO、issue 文本中生成需求。
- 从剪贴板或本地文档导入。

核心产物：

- 需求标题。
- 背景。
- 用户目标。
- 使用场景。
- 范围边界。
- 非目标。
- 初始验收标准。
- 风险和未知问题。

自动化能力：

- 自动补全需求说明。
- 自动识别歧义点。
- 自动生成澄清问题。
- 自动拆分过大的需求。
- 自动推荐关联历史会话。

流转条件：

- 需求有明确目标。
- 至少包含一个可验证的验收标准。
- 范围边界不为空。
- 未解决的阻塞问题为 0，或用户明确允许带风险进入方案设计。

需要人工确认的情况：

- 需求目标不清。
- 验收标准无法测试。
- 影响范围过大。
- 涉及删除数据、支付、权限、安全等高风险能力。

### 4.3 阶段二：方案设计与评审

目标：

把需求转为产品方案，而不是直接进入技术实现。

核心产物：

- 用户流程。
- 页面/模块变化。
- 信息架构。
- 状态与边界情况。
- 交互规则。
- 验收用例。
- 产品风险。
- 版本范围。

自动化能力：

- 自动生成产品方案。
- 自动生成用户故事。
- 自动生成验收清单。
- 自动做产品评审。
- 自动发现范围膨胀、遗漏状态和不可验收描述。
- 自动与历史类似功能对比。

评审维度：

- 是否解决原始需求。
- 是否有明确用户路径。
- 是否覆盖空状态、错误状态、加载状态。
- 是否可验收。
- 是否符合当前产品形态。
- 是否存在不必要的复杂度。

流转条件：

- 产品方案评审通过。
- 验收标准可执行。
- UI/交互范围明确。
- 没有 P0/P1 产品风险。

### 4.4 阶段三：技术方案与评审

目标：

把产品方案转为可实施的工程计划。

核心产物：

- 影响文件和模块。
- 数据模型变更。
- API 设计。
- 前端组件设计。
- 本地任务/后台任务设计。
- 测试策略。
- 迁移策略。
- 回滚策略。
- 风险清单。

自动化能力：

- 自动扫描代码库。
- 自动识别相关模块和既有模式。
- 自动生成技术方案。
- 自动生成任务拆分。
- 自动生成测试计划。
- 自动评审方案。
- 自动估算变更风险。

评审维度：

- 是否复用现有架构。
- 是否引入不必要依赖。
- 数据迁移是否安全。
- 是否有测试闭环。
- 是否影响本地/云端两个模式。
- 是否存在权限、安全、并发、性能问题。

流转条件：

- 技术方案评审通过。
- 任务拆分清晰。
- 测试命令明确。
- 需要人工确认的高风险操作已确认。

### 4.5 阶段四：开发编码与单元自测

目标：

自动调用 AI Coding 工具完成开发，并运行单元级验证。

核心产物：

- 代码变更。
- 变更摘要。
- 单元测试。
- 单元测试结果。
- lint/typecheck 结果。
- 自动修复记录。

自动化能力：

- 自动生成实现任务 prompt。
- 自动调用本地 AI Coding CLI。
- 自动读取代码变更。
- 自动运行测试命令。
- 自动分析失败。
- 自动让 AI 修复失败。
- 自动循环直到通过或达到上限。

建议执行器抽象：

```text
Executor
- name: codex | claude-code | shell
- capabilities: edit_files, run_tests, inspect_git_diff
- run(task, context) -> result
```

自动修复循环：

1. 执行开发任务。
2. 读取 git diff。
3. 运行 unit test/lint/typecheck。
4. 若失败，提取错误摘要。
5. 生成修复任务。
6. 重试，直到通过或达到最大次数。

流转条件：

- 代码变更存在且与任务相关。
- 单元测试通过。
- typecheck/lint 通过，或被明确标记为非阻塞。
- 自动 review 无 P0/P1 问题。
- git diff 未包含无关大规模改动。

必须人工确认的情况：

- 删除大量文件。
- 修改认证、权限、支付、数据删除逻辑。
- 执行破坏性命令。
- 测试长期失败但 AI 试图跳过测试。
- 变更范围明显超出技术方案。

### 4.6 阶段五：集成测试

目标：

验证多个模块组合后的真实行为。

核心产物：

- 集成测试计划。
- 测试环境配置。
- 测试执行结果。
- 失败截图/日志。
- 修复记录。

自动化能力：

- 自动启动本地服务。
- 自动运行 API 测试。
- 自动运行 Playwright/E2E 测试。
- 自动检查页面关键状态。
- 自动截图。
- 自动分析失败原因。
- 自动修复并重跑。

适合桌面版的集成测试：

- App 启动后 Dashboard 正常渲染。
- 数据源扫描完成。
- 会话列表可打开。
- 搜索可用。
- 流水线项目可创建。
- 阶段状态可流转。
- 本地数据库读写正常。

流转条件：

- 集成测试全部通过。
- 关键路径截图正常。
- 没有阻塞级日志错误。
- 数据迁移和回滚策略已验证，若本次涉及迁移。

### 4.7 阶段六：需求验收

目标：

按照最初需求验收标准判断是否完成，而不是只看测试是否通过。

核心产物：

- 验收报告。
- 验收标准逐项结果。
- 证据链接：会话、截图、测试日志、diff。
- 未完成项。
- 变更说明。

自动化能力：

- 自动读取原始需求和验收标准。
- 自动检查功能实现证据。
- 自动生成验收报告。
- 自动标记通过/失败/需人工确认。
- 自动识别需求偏离。

流转条件：

- 所有 P0/P1 验收标准通过。
- 未完成项均为可接受的后续事项。
- 用户可选择自动通过低风险验收，也可手动确认。

必须人工确认的情况：

- UI/体验主观判断。
- 需求文字本身不够可验证。
- 涉及真实用户数据。
- 涉及对外发布。

### 4.8 阶段七：发布

目标：

把已验收的变更按安全策略发布。

个人桌面版的发布可分为两类：

- 本地版本发布：打包桌面 App。
- 项目内功能发布：生成 release note、commit、tag、构建产物。

核心产物：

- 发布清单。
- 版本号。
- changelog。
- 构建结果。
- 发布包。
- 回滚说明。

自动化能力：

- 自动生成 changelog。
- 自动执行 build。
- 自动执行 tauri build。
- 自动生成发布包。
- 自动生成 git commit message。
- 自动创建 tag。
- 自动生成 release notes。

流转条件：

- 需求验收通过。
- build 通过。
- 发布命令在白名单内。
- 工作区无未解释的无关改动。

必须人工确认的情况：

- 推送远端仓库。
- 创建公开 release。
- 上传安装包。
- 发布到应用商店。
- 执行任何不可逆操作。

## 5. 自动流转机制

### 5.1 状态机

建议把流水线实现为显式状态机。

阶段状态：

- `not_started`
- `running`
- `waiting_review`
- `blocked`
- `passed`
- `failed`
- `skipped`

流转动作：

- `start`
- `submit_artifact`
- `request_review`
- `approve`
- `reject`
- `auto_pass`
- `block`
- `retry`
- `rollback`
- `advance`

每次状态变化写入 `pipeline_events`，保证可追溯。

### 5.2 自动流转条件

自动流转只在满足以下条件时发生：

- 当前阶段必需产物齐全。
- 当前阶段质量门禁通过。
- 当前阶段评审无阻塞问题。
- 变更风险低于用户设置阈值。
- 下一阶段输入已生成。
- 没有需要人工确认的动作。

### 5.3 风险分级

建议引入风险等级：

- P0：必须人工确认，不允许自动流转。
- P1：默认阻塞，用户可配置是否自动流转。
- P2：可自动流转，但进入报告。
- P3：信息提示。

P0 示例：

- 删除数据。
- 修改认证/权限。
- 执行发布。
- 执行 destructive shell command。
- 大规模重构。
- 测试失败仍尝试进入下一阶段。

### 5.4 自动化策略配置

用户可配置：

- 是否允许从需求自动进入产品方案。
- 是否允许产品方案自动评审通过。
- 是否允许技术方案自动评审通过。
- 开发修复最大重试次数。
- 测试失败是否自动修复。
- 是否允许自动 commit。
- 是否允许自动 tag。
- 是否允许自动发布。

默认策略应保守：

- 方案和技术方案可自动生成，但默认需要用户确认。
- 编码和测试可自动循环。
- 验收默认需要用户确认。
- 发布默认需要用户确认。

## 6. 新模块信息架构

建议新增一级入口：`流水线`。

页面结构：

- `流水线 Dashboard`：所有项目和待处理项。
- `新建需求`：输入想法，生成需求草案。
- `流水线详情`：一个需求从想法到发布的完整状态。
- `阶段产物`：查看每阶段文档和评审。
- `执行日志`：查看 AI 调用、命令、测试、错误、修复。
- `门禁中心`：集中处理需要人工确认的项。
- `设置`：自动化策略、执行器、命令白名单。

流水线详情建议使用纵向阶段轨道：

```text
需求想法
  -> 方案设计与评审
  -> 技术方案与评审
  -> 开发编码与单元自测
  -> 集成测试
  -> 需求验收
  -> 发布
```

每个阶段卡片展示：

- 当前状态。
- 负责人：AI/用户。
- 最近执行时间。
- 产物数量。
- 门禁结果。
- 下一步动作。

## 7. 与现有功能的结合

### 7.1 会话作为流水线证据

已有会话记录能力可以成为流水线的底层证据：

- 需求来源会话。
- 技术讨论会话。
- 编码执行会话。
- 测试修复会话。
- 验收复盘会话。

建议新增关联表：

- `pipeline_session_links`

字段：

- `pipelineId`
- `stageId`
- `sessionId`
- `linkType`
- `note`

### 7.2 工具调用作为工程事实

已有消息里包含工具调用、命令输出和文件编辑痕迹。流水线可以从这些内容提取：

- 修改过的文件。
- 执行过的命令。
- 测试失败日志。
- 依赖安装。
- 构建错误。
- 关键决策。

这能让流水线不只依赖 AI 自述，而是基于实际执行记录判断进度。

### 7.3 Dashboard 汇总流水线状态

个人桌面版 Dashboard 应加入：

- 进行中的需求数量。
- 阻塞的阶段。
- 待用户确认。
- 今日自动执行次数。
- 最近失败测试。
- 最近发布版本。

## 9. MVP 范围建议

第一版不要直接追求全自动发布。建议 MVP 聚焦：

- 桌面 App 打开即用。
- 本地 Dashboard。
- 会话记录和搜索稳定。
- 流水线项目可创建。
- 需求想法 -> 产品方案 -> 技术方案可以自动生成。
- 阶段评审可以自动生成，但需要用户点确认。
- 编码阶段先只生成任务 prompt，不自动改代码。

第二版再加入：

- 自动调用 AI Coding CLI。
- 自动运行单元测试。
- 自动修复循环。

第三版加入：

- 集成测试。
- 验收报告。
- 发布自动化。

这样做能尽早形成可用桌面产品，同时避免一开始就把高风险自动执行、测试、发布全部耦合进去。

## 10. 关键设计原则

1. 自动生成不等于自动通过。
2. 自动编码不等于自动发布。
3. 每个阶段必须有产物。
4. 每次流转必须有门禁结果。
5. 每个自动动作必须有日志。
6. 高风险动作必须人工确认。
7. AI 结论必须尽量绑定证据：diff、测试日志、截图、会话记录。
8. 本地优先，云端可选。
9. 默认策略保守，用户可逐步放开自动化。
10. 流水线应服务个人效率，不应变成复杂项目管理系统。

## 11. 下一步建议

优先启动两个并行方向：

- 桌面化基础：补齐 Tauri App 壳、启动体验、本地配置。
- 流水线模型：先实现数据模型、状态机、阶段页面和手动流转。

完成这两部分后，再逐步把 AI 生成、评审、编码执行和测试执行接入流水线。
